# AI Tycoon Hub：UI 佈局與 RWD 行為規範

文件版本：1.1  
整理日期：2026-09-23  
規範基準：本對話最新確認的 Hub 決策；互動原型 v1.4 僅供浮動 UI 行為參照。  
適用範圍：Hub 的空間配置、資訊數量、操作入口、響應式切換、狀態延續與 UX 驗收。

本文件以使用者能否找到入口、完成操作，以及在裝置狀態改變後繼續任務為判定依據。下文「必須」代表驗收要求；「不得」代表不可接受的行為。既有原型不代表本文件列出的所有情境均已完成實機驗收。

城市部分目前僅確認：城市地圖與建築入口位於介面最底圖層，UI 以浮動方式置於其上。建築入口的數量、名稱、排列、位置、互動方式，以及城市地圖的範圍與 RWD 行為均待定，不納入本次規範。

## 1. 使用者任務與佈局目標

| 使用者任務 | 佈局必須提供的能力 | UX 判定依據 |
| --- | --- | --- |
| 知道目前使用的角色與可用資源 | 角色資訊、體力與資產可在 Hub 直接取得 | 不必離開 Hub 才能確認操作所需資源 |
| 區分底圖內容與浮動 UI 的操作範圍 | 城市地圖與建築入口位於最底圖層，UI 浮於其上 | 操作浮動 UI 時，不誤觸下層內容 |
| 了解目前可參與的事件 | 提供有限數量的事件摘要與完整內容入口 | 可以快速查看，也能主動收起事件區以繼續探索城市 |
| 追蹤交流並加入聊天 | 提供有限訊息摘要，點擊即可展開聊天 | 預覽不佔用過多城市操作空間，完整交流仍可到達 |
| 進入其他主要功能 | 五個主要導覽入口持續可達 | 使用者可以離開目前任務並找到下一個目的地 |
| 在旋轉、視窗變動後繼續操作 | 重新配置空間並保留任務狀態 | 不重複輸入、不重新尋找閱讀位置、不被帶往其他功能 |

## 2. 共用的空間與操作規則

### 2.1 底圖層與浮動 UI

1. 城市地圖與建築入口位於介面的最底圖層。
2. HUD、事件、快捷工具、聊天摘要與主要導覽以浮動 UI 的方式置於底圖層之上。
3. 浮動 UI 的實際控制或面板範圍接收對應操作；其空白容器不得形成額外的操作阻擋。
4. 使用者操作浮動 UI 時，不得同時觸發其下方內容。

### 2.2 三種安全範圍

| 範圍 | 需考慮的限制 | 必須達成的結果 |
| --- | --- | --- |
| 裝置安全範圍 | 系統保留區、瀏覽器可用視窗 | 關鍵操作不被系統介面遮住 |
| Hub 操作安全範圍 | HUD、兩側控制、事件區與底部操作區 | 浮動 UI 的操作範圍不互相阻擋，也不誤觸下層內容 |
| 任務面板安全範圍 | 開啟中的面板、輸入鍵盤、內容捲動區 | 輸入、提交、關閉與返回操作持續可達 |

### 2.3 空間不足時的優先順序

1. 先保留目前任務的必要操作，包括輸入、提交、關閉與返回。
2. 保留主要導覽與必要資源入口的可達性。
3. 減少摘要資訊的佔用，例如訊息預覽數量與非必要的摘要內容。
4. 完整內容過多時，由所屬面板承擔捲動。
5. 在極短視窗或內容放大到無法容納時，允許必要的垂直捲動；不得以裁切或無法操作的控制來維持一屏。
6. 不得產生非必要的頁面級橫向捲動。

## 3. 區域配置與 UX 責任

| 區域 | 直屏／窄幅配置 | 橫屏配置 | UX 責任 |
| --- | --- | --- | --- |
| Player HUD | 頂部；角色資訊在左，體力與資產水平排列於右 | 頂部；角色資訊在左，體力與資產位於快捷工具之前 | 同一區域完成角色與資源確認 |
| Secondary Event | 左側垂直排列：任務、七日簽到、成就 | 左側垂直排列，順序相同 | 維持活動入口的位置記憶 |
| 快捷工具 | 右側由上而下：Menu、Shop、Mail | HUD 最右側由左至右：Mail、Shop、Menu | 配合方向調整位置，保留功能及操作結果 |
| Live Event | HUD 下方的單行事件摘要，點擊展開 | 右上事件區，可收起為右側事件入口 | 支援快速了解與主動減少資訊佔用 |
| 城市地圖與建築入口 | 位於最底圖層；其他佈局待定 | 位於最底圖層；其他佈局待定 | 與浮動 UI 保持明確的操作層級 |
| Social Live | 主要導覽上方，最多三則訊息 | 左下方，最多兩則訊息 | 提供交流線索並保留城市操作空間 |
| Primary Nav | 最底部，由左至右排列 | 右下方，由左至右排列 | 提供固定的主要目的地與返回路徑 |

## 4. 各區域的行為規範

### 4.1 Player HUD

- 角色資訊包含 Agent 頭像、名稱與 VIP 身分資訊；本規範不要求頭像本身具備額外操作。
- 直屏時，頭像位於角色資訊左側，VIP 固定在名稱下方。
- 橫屏時，角色資訊維持群組關係，資源資訊位於其右方。
- 體力與資產水平排列；各自的補充入口位於對應數值右側，操作對象不得混淆。
- 每組資源資訊可作為同一操作範圍，避免使用者只能命中數值旁的局部位置。
- 橫屏最右側保留 Mail、Shop、Menu，不得讓資源內容將這三個功能推出可操作範圍。
- 角色名稱或資產內容變長時，必須先處理內容容納問題，不得覆蓋相鄰操作。

### 4.2 Secondary Event 與快捷工具

- 任務、七日簽到、成就的相對順序在兩種配置下相同。
- 直屏兩側控制從相同的佈局區段開始排列，使使用者容易定位兩組入口。
- 快捷工具依第 3 節切換排列；每個入口在兩種配置下必須執行同一功能。
- 鍵盤焦點順序必須跟隨當前配置中的操作順序。
- 同一功能在當前配置下只保留一個可操作實例，避免重複焦點或重複觸發。

### 4.3 Live Event

**共用內容限制**

- Hub 同時提供的熱門事件摘要最多三筆。
- 可用事件不足三筆時，只呈現實際可用項目；不得以重複內容補足數量。
- 摘要與完整事件內容必須對應同一事件。

**直屏行為**

- 預設只提供一筆事件摘要，依序輪替可用事件。
- 點擊摘要後，可存取完整事件列表及個別事件內容。
- 使用者正在操作摘要、閱讀展開內容，或頁面不在前景時，停止自動輪替，避免閱讀目標改變。
- 自動輪替不得更改鍵盤焦點，也不得自動開啟事件。

**橫屏行為**

- 首次進入時預設展開事件區。
- 使用者可收起事件區，收起後於右側保留事件入口。
- 點擊該入口重新展開事件區。
- 收起後減少事件區的空間佔用，並保留重新展開的操作入口。
- 可用高度不足時，事件內容可在自身區域內捲動；收合或返回操作必須可達。

**狀態延續**

- 橫屏的展開／收起選擇在本次頁面使用期間保留。
- 切到直屏後使用直屏摘要模式；再次回到橫屏時，恢復先前的展開／收起選擇。
- 跨頁面重新載入或跨裝置保存偏好，不列為本規範要求。

### 4.4 Social Live 與完整聊天

- 直屏預覽最多三則；橫屏預覽最多兩則。
- 「兩則／三則」是 Hub 預覽的數量限制，不是聊天記錄的資料限制。
- 方向切換只改變預覽數量，不刪除訊息，也不重新排列訊息來源提供的順序。
- 訊息不足上限時，使用實際訊息數量，不重複補足。
- 每則預覽限定一行，避免單一長訊息使底部操作區持續增高；完整內容從聊天面板取得。
- 預覽區只包含訊息，不加入標題、分頁、頭像或時間。
- 整個預覽區均可作為完整聊天的入口。
- 橫屏聊天與主要導覽共用底部區段；聊天數量減少後，該區段必須同步減少佔用，減少常駐 UI 的空間佔用。
- 在完整聊天內旋轉或改變視窗時，必須保留已輸入但尚未送出的內容及目前閱讀位置。

### 4.5 Primary Nav

- 固定五個目的地，由左至右為：大廳、事件、商會、排行、我的。
- 直屏與橫屏不得交換目的地的相對順序。
- 版型切換不得改變使用者目前所在的主要功能。
- 訊息與事件增加時，不得將主要導覽推離正常支援視窗的操作範圍。

## 5. RWD 模式選擇邏輯

### 5.1 配置判斷

以目前可用的佈局視窗判斷，不依手機品牌、裝置型號或作業系統選擇配置。

| 條件 | 採用配置 |
| --- | --- |
| 視窗為直向 | 直屏／窄幅配置 |
| 視窗為橫向，且寬度達橫屏門檻 | 橫屏配置 |
| 視窗為橫向，但寬度不足門檻 | 直屏／窄幅配置 |

目前原型使用 `orientation: landscape` 與 `min-width: 36rem` 同時成立作為橫屏門檻。此門檻是配置切換條件；各區域在同一配置內仍須持續適應可用空間。

### 5.2 重新計算的順序

1. 取得目前可用視窗與裝置安全範圍。
2. 判斷應採用直屏／窄幅配置，或橫屏配置。
3. 套用該配置的區域位置、快捷工具順序與摘要數量上限。
4. 納入事件區是否展開、任務面板是否開啟等使用者狀態。
5. 重新配置浮動 UI，維持其位於城市地圖與建築入口之上的層級關係。
6. 檢查浮動 UI 的關鍵操作是否被遮住，以及是否出現非必要的頁面捲動。

### 5.3 不可因配置切換而重設的狀態

- 目前所在的主要功能與已選擇的目的地。
- 開啟中的事件或聊天內容。
- 尚未送出的輸入內容。
- 完整內容的閱讀位置。
- 本次使用期間的橫屏事件收合選擇。
- 正在操作的功能及其鍵盤焦點；若原控制不再存在，焦點轉移到同一功能的替代入口。

方向切換只改變操作空間，不得導致重複提交、自動關閉任務、資料清除或功能跳轉。

## 6. 特殊視窗狀態與內容增長

| 情境 | 處理規則 | UX 目的 |
| --- | --- | --- |
| 瀏覽器工具列展開或收起 | 依新的可用高度重新配置 | 底部控制不被工具列遮住 |
| 系統保留區改變 | 重新套用裝置安全範圍 | 操作不落在系統佔用區 |
| 輸入鍵盤開啟 | 優先保留輸入、送出及關閉操作；鍵盤造成的高度縮減不得被當成使用者主動旋轉來重設任務 | 持續完成輸入 |
| 開啟面板時旋轉 | 調整面板可操作範圍，保留內容與狀態 | 不必重新開啟或重新輸入 |
| 訊息或事件內容較長 | 摘要遵守原數量與行數限制；完整內容由所屬面板處理 | 避免單筆資料主導整個 Hub 的佈局 |
| 文字或頁面內容被使用者放大 | 優先確保內容與操作可達；必要時允許垂直捲動 | 尊重使用者的閱讀需求 |
| 極短視窗 | 使用受控捲動及內容精簡，不移除關鍵功能 | 保持任務可完成性 |
| 連續快速旋轉或縮放 | 以最新的有效視窗狀態完成重排，不累積過期位置 | 防止錯位或誤觸 |
| 使用者要求減少動態效果 | 不依賴自動輪替取得任何功能或內容；提供直接操作路徑 | 使用者可以掌握閱讀與操作節奏 |

## 7. 操作與閱讀連續性

1. 同一操作入口的意義與結果不得因方向改變。
2. 重新排列後，鍵盤操作順序需對應當前區域順序，不沿用已失效的位置關係。
3. 面板開啟後，操作範圍必須明確，不能同時操作其下方的 Hub。
4. 面板關閉後，回到原入口；原入口因配置改變而不可用時，回到等價入口。
5. 內容更新不得自行移動操作焦點，也不得打斷使用者正在閱讀的完整內容。
6. 容器的空白範圍、已收起的內容與當前不使用的控制，不得形成不可見的操作阻擋。
7. 旋轉過程不得把原本指向某功能的操作誤判為另一功能的操作。

## 8. UX 驗收情境

以下為驗收條件，不是已完成測試的聲明。

| 編號 | 操作情境 | 通過條件 |
| --- | --- | --- |
| UX-01 | 在直屏開啟 Hub | 頂部可確認角色與資源；左側活動入口及右側 Menu／Shop／Mail 可達；聊天最多三則 |
| UX-02 | 在橫屏開啟 Hub | HUD 最右側為 Mail／Shop／Menu；事件位於右上；聊天位於左下且最多兩則；主要導覽位於右下 |
| UX-03 | 確認介面層級 | 城市地圖與建築入口位於最底圖層，浮動 UI 位於其上；操作浮動 UI 不觸發下層內容 |
| UX-04 | 直屏旋轉為橫屏，再轉回 | 主要功能與資料不重設；工具順序與聊天數量依配置改變；浮動 UI 與底圖層的層級關係維持一致 |
| UX-05 | 收起橫屏事件，再旋轉往返 | 收起後仍有右側事件入口；直屏使用摘要；回橫屏恢復收起狀態 |
| UX-06 | 點擊 Social Live | 開啟完整聊天；第三則及其他訊息不因橫屏預覽上限而遺失 |
| UX-07 | 聊天輸入至一半時開啟鍵盤或旋轉 | 輸入保留，送出與關閉可達，不自動提交 |
| UX-08 | 事件、訊息或角色名稱變長 | 不遮住相鄰控制，不推走主要導覽；完整內容仍可取得 |
| UX-09 | 收合、開啟及關閉面板 | 不觸發下層內容；關閉後可回到原本操作流程 |
| UX-10 | 使用鍵盤依序操作快捷工具 | 焦點順序與當前配置中的順序一致 |
| UX-11 | 工具列、安全區或視窗高度改變 | 底部及邊緣操作不被遮住，沒有不可見的攔截區 |
| UX-12 | 窄幅、短橫屏、內容放大 | 功能持續可達；正常範圍一屏可操作，例外條件採必要的垂直捲動；沒有非必要橫向捲動 |
| UX-13 | 查看主要導覽 | 導覽固定為大廳、事件、商會、排行、我的 |
| UX-14 | 多次快速切換方向 | 最終版型對應最新視窗，沒有重複控制、重複提交或殘留阻擋 |

### 驗收覆蓋範圍

- 直屏寬度涵蓋約 320–430 CSS px。
- 橫屏寬度涵蓋約 667–932 CSS px，包含可用高度受限的情況。
- 必須包含事件展開、事件收起、完整聊天開啟、鍵盤開啟與方向切換中的狀態。
- 視窗模擬只能證明對應條件下的結果；發布前仍應以目標手機瀏覽器驗證工具列、系統安全區與輸入鍵盤行為。

## 9. 規範維護原則

- 修改任一區域的佔用方式時，必須確認主要導覽與當前任務仍可操作，且浮動 UI 與底圖層的操作不互相誤觸。
- 修改直屏或橫屏配置時，必須同步檢查另一配置及兩者之間的切換。
- 新增資訊時，先確認是否影響現有摘要上限與操作路徑；不得直接擴大常駐區域而擠壓必要入口。
- 功能內容、資料來源與交易流程由各功能規格負責；本文件只約束其在 Hub 中的可達性與佈局行為。
